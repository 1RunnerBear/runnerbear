# RunnerBear v10.21 — Performance & Stability Foundation

## Scope and invariants

v10.21 changes loading, rendering, synchronization, caching and observability. The v10.20 visual design, coaching decisions, state keys, Garmin/Tredict contracts and user flows remain unchanged. Historical assets remain in Git for rollback, but are no longer loaded by `index.html`.

## Root causes in v10.20

1. `index.html` loaded 38 CSS files and 43 JavaScript files, including many historical runtime and override layers.
2. `runnerbear-v107-coach-os.js` mounted Today, Plan, Goals and More on every `renderAll()` call. Startup performed that full mount immediately and again after 500 ms and 1400 ms.
3. Initialization polled every 50 ms until dependencies appeared. Visibility and storage events scheduled additional full-app renders.
4. Cloud startup requested a 365-day full bootstrap and synchronously waited for a Tredict synchronization before returning it.
5. The Cloud client scanned all eligible localStorage keys after every click, change and five-second interval, even when state was unchanged.
6. Authenticated reads executed `ensureUser()`, adding a D1 write to read-only request paths.

## Implemented architecture

- `runnerbear-core-v1021.js`: deterministic plan, analysis and coaching models plus the cached recovery adapter.
- `runnerbear-ui-v1021.js`: the canonical UI. It renders Today initially and mounts Plan, Goals or More only when that view becomes active.
- `runnerbear-data-v1021.js`: asynchronous Cloud/Tredict integration, dirty-state persistence and lazy full bootstrap.
- `runnerbear-v1021.css`: one ordered stylesheet generated from the active v10.20 design sources and the v10.21 shell rules.
- `runnerbear-v1021-assets.json` and `scripts/build-v1021.mjs`: reproducible source manifest and build step. CI fails if committed canonical assets are stale.

Navigation has one delegated listener. Surface handlers are rebound only inside the surface that was rendered. Storage events are filtered and coalesced into one animation frame. Visibility changes refresh Cloud data only when the home snapshot is older than five minutes; hiding the page flushes dirty local state without rendering the UI.

## Bootstrap and persistence

- First render uses cached local state immediately.
- `/api/bootstrap/home` returns only Today-relevant local state, 35 days of activities, 21 days of recovery signals and the latest 30 capacity rows.
- The full 365-day bootstrap is loaded only on the first visit to Plan, Goals or More.
- Tredict synchronization is background work and no longer blocks either bootstrap response.
- localStorage is uploaded only after RunnerBear emits `runnerbear:state-dirty`; repeated changes are debounced and identical snapshots are skipped.
- A controlled cached-data message is shown when the home bootstrap fails.

## D1 and caching

The new home queries use the existing production indexes:

- `idx_rb_activities_user_date (user_id, date DESC)`
- `idx_rb_health_user_date (user_id, date DESC)`
- `idx_rb_capacity_user_timestamp (user_id, timestamp DESC)`

No speculative migration was added. Read-only routes no longer call `ensureUser()`. Versioned canonical assets and hero images receive one-year immutable cache headers; `index.html` remains `no-cache`.

## Before/after measurements

Measurements are deterministic from the asset references in the v10.20 and v10.21 `index.html` files. Compression uses Node's gzip level 9 and Brotli defaults.

The repository does not contain authenticated browser traces for v10.20, so a wall-clock first-useful-view number is intentionally not fabricated. v10.21 records `runnerbear:startup` and per-surface render measures through the Performance API, and emits structured client and Worker bootstrap durations for production comparison after rollout.

## Observability and failure behavior

Structured JSON events cover:

- frontend initialization errors and unhandled promise rejections;
- home/full client bootstrap duration and controlled bootstrap failures;
- home/full Worker response and D1 duration;
- Tredict sync duration and errors.

Cached data remains usable if Cloud bootstrap fails. Missing critical core dependencies stop startup with a visible recovery message instead of entering a 50 ms retry loop.

## Validation

- JavaScript syntax checks for all canonical assets and Worker entry points.
- 54 Node tests covering legacy v10.13–v10.20 behavior plus v10.21 asset loading, targeted rendering, cached recovery, lazy bootstrap, dirty-state persistence, D1 query/index alignment and release metadata.
- Manifest and local asset validation in GitHub Actions.
- Production workflow health gate requires assets, D1, RunnerBear Cloud v10.21 and the existing Tredict RPC v10.8.1 before the deploy is accepted.
