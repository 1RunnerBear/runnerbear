# RunnerBear v11.3 — One Decision Coach Experience

Status: **LOCKED**  
Release: `11.3.0`  
Product concept: `One Decision Coach Experience`  
Visual direction: `Concept 1 · Premium calm`  
Locked: `2026-08-28`

## 1. Outcome

RunnerBear v11.3 shall answer one question before anything else:

> What is the right next action for me today, and why?

The Today surface must combine the canonical plan, Bakken Adaptive Coach, Body Response, completed activity state and Coach Live into one current decision. It must not ask the athlete to reconcile several cards, scores or competing recommendations.

## 2. Product contract

1. There is exactly one authoritative daily decision on the Today surface.
2. The decision is derived from the active canonical plan revision and the current deterministic coach decision. It is not generated by the language model.
3. The first screen shows one headline, one concise explanation, at most three evidence items and one visually dominant primary action.
4. Body Response is supporting evidence, not a competing recommendation or a new navigation destination.
5. Coach Live explains the same decision and can open an existing validated action flow. It never writes a plan or invents a proposal.
6. A plan mutation requires a deterministic proposal, a visible before/after comparison and explicit confirmation.
7. A committed mutation remains reversible through the existing canonical plan undo flow.
8. A stale, mismatched or incomplete decision is never presented as current. The safe fallback is to refresh data, complete a check-in or leave the plan unchanged.
9. Positive recovery signals may support the planned dose but never increase duration, distance or intensity.
10. Illness, pain and acute-symptom boundaries remain conservative and cannot be overridden by Coach Live.

## 3. One Decision data contract

The Worker adds `oneDecision` to the existing `/api/v2/bootstrap` response. This preserves the current request budget and guarantees that decision and plan data arrive atomically.

```json
{
  "version": "one-decision-1",
  "planRevisionId": "...",
  "inputCursor": "...",
  "generatedAt": "...",
  "validUntil": "...",
  "freshness": "current",
  "state": "follow",
  "tone": "calm",
  "headline": "Følg dagens økt",
  "summary": "...",
  "workout": {},
  "evidence": [],
  "primaryAction": {
    "kind": "open_workout",
    "label": "Åpne dagens økt"
  },
  "secondaryActions": [],
  "proposal": null,
  "safety": {
    "planWritesByAi": false,
    "confirmationRequired": true,
    "undoAvailable": true,
    "maximumReductionPercent": 20
  }
}
```

Allowed states:

| State | Meaning | Primary action |
| --- | --- | --- |
| `follow` | Current signals support the plan | Open workout |
| `adjust` | Deterministic coach has a bounded proposal | Review proposal |
| `clarify` | Pain, illness or subjective input is needed | Complete body check-in |
| `refresh` | Decision is stale, mismatched or data is insufficient | Refresh Garmin data |
| `completed` | Today's workout already has a terminal result | View result |
| `rest` | Today is a planned rest day | View plan context |

Contract invariants:

- `version` is exactly `one-decision-1`.
- `planRevisionId` matches both the bootstrap and active plan revision.
- For an active training recommendation, `freshness: current` requires a non-expired deterministic decision on the same plan revision. A terminal result or planned rest state may be current from the canonical plan status alone.
- `evidence` contains zero to three plain-language items with stable IDs and source labels.
- `proposal` can exist only for a current `reduce` decision with `status: proposed`.
- `proposal.reductionPercent` is greater than zero and no more than 20.
- `primaryAction.kind` is one of the locked action enum values; arbitrary URLs and commands are forbidden.
- The browser rejects a mismatched envelope and falls back to the existing safe view.

## 4. Authority and mutation flow

The existing D1 model remains the only persistent authority:

- `rb_plan_revisions` owns plan history.
- `rb_coach_decisions` owns deterministic proposals and their resolution status.
- `rb_sync_operations` owns durable outbound Tredict synchronization.
- `rb_coach_live_*` owns immutable conversation history only.

v11.3 introduces no new state table and no second decision store.

The accepted mutation flow is:

1. One Decision exposes a deterministic proposal already attached to the current coach decision.
2. The browser opens a before/after review without modifying local or remote state.
3. The athlete explicitly chooses `Bruk redusert dose` or `Behold planen`.
4. The existing decision resolve route validates status, TTL, plan revision and bounded change.
5. Acceptance creates and commits one canonical plan revision and queues durable sync.
6. The UI refreshes bootstrap and shows the resulting canonical state.
7. The existing plan undo endpoint restores the parent revision when requested.

Coach Live may expose a button that opens step 2. It may not call steps 4–7 itself and may not convert free text into a plan mutation.

## 5. UX and information hierarchy

The Today surface order is locked:

1. App bar and goal context.
2. One Decision hero.
3. Weekly priority and relevant change/status feedback.
4. Compact supporting insight.
5. Sync status.

The old top-level stack of separate workout, Body Response, deterministic coach and Coach Live cards is removed when a valid One Decision envelope is available. Existing components remain as compatibility fallback if the v11.3 envelope is unavailable.

The hero contains:

- status eyebrow and freshness;
- decision headline and concise summary;
- today's workout identity and essential dose;
- at most three evidence chips;
- one filled primary action;
- low-emphasis secondary actions: `Spør coach` and `Se grunnlaget` when relevant.

The plan proposal sheet contains:

- the reason for the adjustment;
- current versus proposed dose;
- the exact percentage reduction;
- the statement that only the listed workout is affected;
- a filled confirmation action;
- a neutral keep-plan action;
- close/backdrop/Escape behavior with no state change.

## 6. Coach Live experience

Coach Live receives a minimized `oneDecision` object in its server-built context. The system instruction makes these boundaries explicit:

- explain the current decision first;
- distinguish canonical facts from general advice;
- never claim that a plan has changed;
- never create an alternative plan proposal;
- direct the athlete to RunnerBear's structured confirmation flow when a proposal exists;
- preserve medical redirection and conservative uncertainty language.

The Coach Live sheet may show one structured RunnerBear action above the conversation. This action is rendered from `oneDecision.primaryAction`; it is not parsed from model output.

## 7. Design requirements

The visual system remains Concept 1 / Premium calm:

- warm neutral surface, restrained contrast and one controlled accent;
- hierarchy through type, spacing and surface depth rather than multiple saturated status colors;
- no readiness score, gauge, traffic-light dashboard or anthropomorphic avatar;
- the primary action is the only filled control in the hero;
- evidence uses compact, readable labels rather than dense metrics;
- movement is limited to short opacity/translate feedback and disabled under reduced-motion preference;
- mobile sheets use the existing full-height pattern and preserve safe-area spacing.

## 8. Accessibility requirements

- Semantic heading order and a named decision region.
- Dialogs use `role="dialog"`, `aria-modal="true"` and a stable `aria-labelledby` target.
- The decision status and async mutation result are available to assistive technology.
- Interactive targets are at least 44 CSS pixels; primary actions are at least 48 pixels.
- Visible `:focus-visible` treatment meets contrast requirements.
- No meaning depends on color alone.
- Loading controls are disabled and retain clear text.
- Escape and backdrop close proposal/reason dialogs without committing.
- Focus moves to the first useful control after opening a dialog.

## 9. Performance requirements

- The app keeps the existing four static production requests: HTML, CSS, core bundle, UI/data bundles as currently composed.
- No new request is added to initial bootstrap.
- v11.3 CSS is compiled into the canonical stylesheet.
- The One Decision builder is pure, bounded and performs no I/O.
- Bootstrap augmentation parses only the bounded JSON response already produced by the Worker.
- Coach Live continues to stream responses and persists the assistant branch through `ctx.waitUntil`.
- No polling, client-side LLM inference, large image asset or additional font is introduced.

## 10. Observability and privacy

- Health reports `cloudBuild: 11.3.0`, `oneDecision: true`, `oneDecisionVersion: one-decision-1` and a passing capability audit.
- Client telemetry records only action/state identifiers, not health metric values or conversation content.
- One Decision adds no new persistent health storage.
- Coach Live retains the existing sanitized, minimized context and rate limit.
- Logs contain release, state and decision identifiers; no raw health payload or prompt text.

## 11. Release gates

The release may deploy only when all of the following pass:

- deterministic build and generated-bundle diff check;
- full Node test suite and v11.3 contract tests;
- Worker syntax validation and Wrangler dry-run;
- unchanged 14-table schema audit;
- One Decision contract, revision mismatch, expiry and 20% bound tests;
- zero plan-write SQL in the Coach Live module;
- UI test for one primary action, no new navigation tab, accessible proposal sheet and four-request asset budget;
- production D1 backup and history-preservation audit;
- remote migration command (expected no-op for v11.3);
- production `/health` confirms v11.3, schema 4, One Decision, Coach Live, Body Response, Bakken, D1, history and Tredict health;
- private access guard remains active.

## 12. Explicit non-goals

- No fifth navigation tab for health or coach.
- No autonomous LLM plan editing.
- No open-ended tool calling from Coach Live.
- No readiness number or composite health score.
- No dose increase based on positive recovery data.
- No new D1 migration or duplicated decision table.
- No voice mode, avatar, push notification or background agent in this release.

## 13. Acceptance statement

v11.3 is accepted when an athlete can open Today, understand the current recommendation in one scan, see why it applies, take one safe next action, ask Coach Live for explanation, review any proposed plan reduction before confirmation and undo a committed change — without contradictory recommendations, a new request on first load or a second source of truth.
